# Task 3.4 — Ensure data quality (D3)
Tags: ✓ verified 2026-10-20 (link) · ~ established, not re-fetched. Skills 3.4.1–3.4.5.

## 1. Dimensions of data quality (use these words in answers)
Completeness (no unexpected nulls) · Uniqueness (no duplicates) · Validity (format/range/domain) · Accuracy · Consistency (across systems/time) · Timeliness/freshness · Integrity (referential) · Volume/row-count anomalies · Schema conformance.

## 2. Quality checks while processing (3.4.1)
Where to check: at **ingest** (Lambda/S3-event validation, Firehose transform, Glue crawler classification), **in transform** (Glue Data Quality, Deequ on Spark/EMR, DataBrew), **before publish** (gate in Step Functions Choice), **after load** (Redshift/Athena SQL assertions, DMS validation ~).
Actions on failure: fail the job; quarantine bad rows to a `rejected/` prefix; continue but alert; route record to DLQ; block downstream steps.

## 3. AWS Glue Data Quality and DQDL (3.4.2) ✓ [DQDL](https://docs.aws.amazon.com/glue/latest/dg/dqdl.html)
- **DQDL** = case-sensitive language; a ruleset is `Rules = [ … ]` (capital R); rule shape `<RuleType> <Parameter> <Expression>`.
- **Rule types ✓**: `ColumnExists`, `ColumnCount`, `ColumnDataType`, `ColumnLength`, `ColumnNamesMatchPattern`, `ColumnValues`, `Completeness`, `IsComplete`, `IsUnique`, `IsPrimaryKey`, `Uniqueness`, `UniqueValueRatio`, `DistinctValuesCount`, `Mean`, `Sum`, `StandardDeviation`, `Entropy`, `ColumnCorrelation`, `RowCount`, `RowCountMatch`, `DatasetMatch`, `AggregateMatch`, `ReferentialIntegrity`, `SchemaMatch`, `DataFreshness`, `CustomSql`, `Distribution`, `DetectAnomalies`, and file-based `FileFreshness/FileMatch/FileUniqueness/FileSize`.
- **Expressions ✓**: `=`, `!=`, `>`, `<`, `>=`, `<=`, `between x and y`, `in [..]`, `not in`, `matches /regex/`, `now()` for dates, **`with threshold`** (percentage of values satisfying; only ColumnValues/ColumnDataType/CustomSql), keywords `NULL`, `EMPTY`, `WHITESPACES_ONLY`.
- **Composite rules**: `(rule1) and (rule2)` / `or` — evaluated per rule over the whole dataset by default; set `compositeRuleEvaluation.method=ROW` for row-wise evaluation ✓.
- **`where` clause** (Glue 4.0 ✓) filters rows for conditional rules; **dynamic rules** compare with history: `RowCount > avg(last(3))` (Glue ETL only ✓); **analyzers** gather statistics without pass/fail; **labels** (≤10 per rule) for reporting.
- Example ruleset:
```
Rules = [
  IsComplete "order_id", IsUnique "order_id",
  ColumnValues "status" in ["NEW","PAID","SHIPPED"],
  Completeness "customer_id" > 0.98,
  ColumnValues "email" matches "[a-zA-Z0-9._%+-]+@[a-zA-Z0-9.-]+" with threshold > 0.95,
  RowCount > avg(last(3)) * 0.8,
  DataFreshness "event_ts" <= 24 hours
]
```
- Run: **Evaluate Data Quality** node in Glue Studio / `EvaluateDataQuality` transform in ETL (can **fail the job**, publish to CloudWatch, output row-level results to isolate bad rows) or evaluate rulesets on **Data Catalog tables** (scheduled, no ETL). Row-level pass/fail columns (`DataQualityRulesPass/Fail`) allow quarantine of failing rows ✓.
- Recommendations: Glue can **recommend** rules from profiling; **anomaly detection** (`DetectAnomalies`) for drift ~.

## 4. Other quality tools
- **DataBrew** ✓ (guide names): profile jobs (stats, correlations), **data quality rulesets** (column/row checks, thresholds), recipes to fix, results to S3; no code.
- **Deequ / PyDeequ** (open-source on Spark; EMR/Glue) ~ — what Glue DQ builds on.
- **Athena/Redshift SQL assertions**, Great-Expectations-style frameworks (not AWS-native ✗).
- **DMS data validation** for source vs target row/column comparison ~.
- **Schema checks**: Glue Schema Registry compatibility, crawler Log policy, `SchemaMatch`.
- Alerting: DQ result → CloudWatch metric → alarm → SNS; EventBridge on Glue DQ result events ~.

## 5. Data consistency (3.4.3)
Compare counts/checksums/aggregates between layers (`RowCountMatch`, `DatasetMatch`, `AggregateMatch`), idempotent upserts (MERGE) to prevent drift, Iceberg ACID snapshots, DMS validation, referential integrity (`ReferentialIntegrity`), eventual consistency awareness (DynamoDB eventually vs strongly consistent reads; GSIs eventually consistent; S3 now strongly consistent ~), reconcile late/duplicate events with event-time + dedupe keys, DataBrew consistency profiling.

## 6. Data sampling techniques (3.4.4)
| Technique | Use |
|---|---|
| Simple random (with seed) | unbiased, reproducible profiling |
| **Stratified** | preserve proportions of segments/categories (rare classes) |
| Systematic (every n-th) | ordered data; beware periodicity |
| Cluster | sample whole groups (cheap for partitioned files) |
| Reservoir | fixed-size sample from a stream of unknown length |
| Head/first-N | biased — avoid for quality conclusions |
Tools: DataBrew sample size settings, Athena `TABLESAMPLE` ~ / `ORDER BY rand() LIMIT`, Spark `sample()/sampleBy()`, Glue DQ on partitions. Sampling trades certainty for cost: profile a representative sample, run full-dataset *rules* for hard constraints.

## 7. Data skew mechanisms (3.4.5)
Skew = uneven key distribution → straggler tasks, OOM, hot shards/partitions. Detect: Spark UI task-time/size spread, Glue metrics, Redshift `SVV_TABLE_INFO.skew_rows` ~, DynamoDB hot key metrics/Contributor Insights ~, Kinesis hot shard. Mitigate:
| Where | Technique |
|---|---|
| Spark/Glue/EMR | **salting** hot keys (key + random salt, two-stage aggregate), `repartition` on better keys, **broadcast join** small side, AQE skew-join handling ~, filter/handle nulls & default keys separately |
| Redshift | choose higher-cardinality DISTKEY; use EVEN/AUTO if no good key |
| DynamoDB | high-cardinality partition key; **write sharding**; on-demand |
| Kinesis/MSK | distribute partition keys; more shards/partitions |
| Athena | avoid skewed partitions; bucket/compact |

## 8. Worked scenarios
1. *Stop publishing when > 5 % of order_id are null* → **Evaluate Data Quality** with `Completeness "order_id" > 0.95`, job set to fail on ruleset failure.
2. *Email must match pattern, no code, every new file* → **DataBrew ruleset** (or Glue DQ rule with `matches … with threshold`).
3. *Profile a 5 TB dataset cheaply but representative per segment* → **stratified + random sampling**.
4. *One customer holds 60 % of rows; executors OOM* → **salting**.
5. *Rows must be separated rather than failing whole job* → row-level DQ results → write failing rows to `rejected/`.

## 9. Keyword → answer and traps
| Keyword | Answer | Trap |
|---|---|---|
| rules language for Glue | DQDL | SQL only |
| stop pipeline on bad data | DQ with fail-job action | crawler |
| compare with previous runs | dynamic rule `last()` | static threshold |
| representative sample | stratified | first N rows |
| hot key OOM | salting / repartition | more workers |
| no-code rulesets | DataBrew | Lambda |
