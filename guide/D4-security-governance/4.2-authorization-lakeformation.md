## 1. Custom IAM policies (4.2.1, 4.2.6)
- Use **AWS managed policies** for quick starts (e.g., `AWSGlueServiceRole`), **customer managed** when they are too broad/narrow, inline only for 1:1 binding.
- Least privilege recipe: specific **actions**, specific **resource ARNs**, **conditions** (prefix, tag, source VPC/IP, MFA, TLS, Region), no `*:*`; start with Access Analyzer–generated policy from CloudTrail activity ~; validate with policy simulator/Access Analyzer checks ~.
- Evaluation logic: explicit **Deny** wins → organization SCPs → permission boundary → session policy → identity/resource allow. Same-account: identity OR resource policy allow suffices; **cross-account**: both sides must allow (unless role assumption) ✓.
- Common data-engineering policy shapes: S3 prefix-scoped Get/Put/List with `s3:prefix` condition; `kms:Decrypt/GenerateDataKey` on the specific key; `glue:GetTable/GetPartitions` on catalog/database/table ARNs; `iam:PassRole` limited with `iam:PassedToService`; `logs:*` on a log group.

## 2. Store application and database credentials (4.2.2)
| | Secrets Manager | SSM Parameter Store |
|---|---|---|
| Purpose | secrets with lifecycle | config + secrets |
| Rotation | **automatic** (managed or Lambda) ✓ | none built-in |
| Cost | per secret/month + API calls | Standard parameters free; Advanced paid ~ |
| Cross-account | resource policy | via sharing Advanced parameters (RAM) ~ |
| Encryption | KMS always | SecureString (KMS) optional |
| Size | up to 64 KB ~ | 4 KB std / 8 KB adv ~ |
Pick: rotation or DB credentials → Secrets Manager; many config values + a few static secrets at lowest cost → Parameter Store SecureString ✓ (mock Q37). Never hard-code or put in env vars/plaintext S3.

## 3. Database users, groups, roles (4.2.3) — Redshift emphasis
- Redshift: database users/groups/**roles** (RBAC) with `GRANT … TO ROLE`, schema `USAGE`, table `SELECT`, **column-level GRANT**, **row-level security** policies, **dynamic data masking** by role, `ALTER DEFAULT PRIVILEGES`; authenticate with IAM (temporary credentials, `GetClusterCredentials`), IAM Identity Center/federation ~; `COPY/UNLOAD/Spectrum` use IAM roles attached to the cluster/namespace; **data sharing** permissions (4.5.1).
```sql
CREATE ROLE analyst;
GRANT USAGE ON SCHEMA sales TO ROLE analyst;
GRANT SELECT ON ALL TABLES IN SCHEMA sales TO ROLE analyst;
GRANT ROLE analyst TO "alice";
```
- RDS/Aurora: IAM database authentication, DB roles/grants, Secrets Manager rotation; DynamoDB: IAM fine-grained access (`dynamodb:LeadingKeys`, `dynamodb:Attributes` conditions ~).

## 4. Lake Formation (4.2.4) ✓ [LF hybrid access](https://docs.aws.amazon.com/lake-formation/latest/dg/hybrid-access-mode.html)
**What it is**: central, fine-grained access control over **Glue Data Catalog** resources and the S3 data behind them, for Athena, Redshift (Spectrum), EMR, Glue (named in 4.2.4 ✓).
- **Model**: register S3 location (role) → grant permissions on catalog objects to principals (IAM users/roles, SAML/IdC users, accounts, orgs): `SELECT, INSERT, DELETE, DESCRIBE, ALTER, DROP, CREATE_TABLE…`, column lists, **data filters** (row-level via filter expression, column-level inclusion/exclusion, **cell-level** = both). Effective access = **LF permission AND the IAM permission** for the calling service (opted-in principals need both ✓).
- **Credential vending**: LF issues scoped temporary credentials to integrated engines for registered locations; June 2026: table grants (SELECT=read, SUPER=read/write) can also govern *direct S3 file access* with EMR 7.13+ (non-English What's New text only [UNVERIFIED]).
- **IAMAllowedPrincipals**: virtual group that, when granted `Super`, makes a resource a plain **AWS Glue resource** — IAM only, LF *not* enforced ✓. To enforce LF, revoke it.
- **Hybrid access mode** ✓: two pathways to the *same* catalog objects — principals you **opt in** use LF permissions (and IAM), all others keep using IAM S3/Glue policies. Registering the S3 location in hybrid mode enforces only CREATE_TABLE, CREATE_PARTITION, UPDATE_TABLE by default. Use to adopt LF gradually without breaking existing jobs; for cross-account, set **cross-account version setting to 4** ✓; to convert an LF resource to hybrid, first opt in current principals and grant `Super` to IAMAllowedPrincipals ✓.
- **LF-tags (LF-TBAC)**: define tags (`domain=finance`, `sensitivity=pii`), attach to databases/tables/columns, grant permissions on tag expressions; scales to thousands of resources; satisfies *tag-based/attribute-based* (4.2.5).
- **Cross-account**: grant to external account/org; recipient admin re-grants to principals; tables appear via **resource links** (shared resource names) created in the recipient catalog; AWS RAM invitations underneath; S3 data in encrypted buckets also needs KMS key policy for the consumer.
- **Governed tables** (older LF feature) no longer in guide → use Iceberg/S3 Tables with LF/IAM. Limitation example ✓: Glue jobs on tables with *cell-level filters* can't use job bookmarks, push-down predicates, or `enableUpdateCatalog`.
- LF vs IAM/S3 policies: IAM/bucket policies = object-level, hard to scale to many tables/columns; LF = table/column/row/cell, central, audited in CloudTrail.

## 5. Authorization methods (4.2.5)
| Method | How | Use |
|---|---|---|
| **RBAC** | permissions bundled in roles/groups (IAM roles, Redshift roles, LF grants to roles) | stable job functions |
| **Policy-based** | explicit allow/deny statements on resources | baseline |
| **Tag-based / ABAC** | `aws:PrincipalTag/team` equals `aws:ResourceTag/team` (IAM) or LF-tags | scalable per-team/project access without per-team policies ✓ (topic mock Q62) |
| Resource-based | bucket/KMS/SQS/Lambda/catalog policies | cross-account, service-to-service |
Pick: many teams × many resources → ABAC/LF-tags; few stable roles → RBAC.

## 6. Least privilege checklist (4.2.6)
Scoped resources, separate roles per pipeline stage (ingest read-only raw; transform write curated), conditions for prefix/VPC/TLS, no wildcard principals in resource policies without conditions (KMS ✓ warning), remove unused permissions (Access Analyzer unused-access findings ~), rotate/avoid long-term keys, MFA for humans, break-glass roles audited.

## 7. Worked scenarios
1. *Analysts see all columns except `ssn` in Athena; central, auditable, least overhead* → **Lake Formation** column grant (not bucket policy/IAM deny).
2. *Existing jobs use IAM only; adopt LF gradually* → **hybrid access mode** ✓.
3. *Hundreds of project prefixes; one policy* → **ABAC** (principal tag = resource tag).
4. *Share lake tables with another account* → LF cross-account grant + resource link (+ KMS key policy).
5. *Support agents see last 4 card digits; finance sees full* → Redshift **dynamic data masking**.

## 8. Keyword → answer and traps
| Keyword | Answer | Trap |
|---|---|---|
| column/row/cell security on lake | Lake Formation (filters) | S3 policy |
| scalable permissions by attribute | LF-tags / ABAC | per-resource grants |
| migrate to LF gradually | hybrid access mode | delete IAM policies |
| LF not enforced | IAMAllowedPrincipals has Super | missing grant |
| rotation of DB secret | Secrets Manager | Parameter Store |
| cross-account needs | allow on both sides | one-sided policy |
| `AccessDenied` from KMS | key policy/IAM kms permissions | S3 bucket policy |
