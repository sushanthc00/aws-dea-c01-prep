## 1. Network-level controls (4.1.1)
| Control | Facts |
|---|---|
| **Security group** | stateful, allow-only, attached to ENIs (Glue connections, Redshift, EMR, RDS, Lambda-in-VPC, interface endpoints); can reference other SGs; Glue needs a **self-referencing** inbound rule so its workers can talk to each other ~ |
| **NACL** | stateless, subnet-level, allow + deny, numbered rules |
| **VPC endpoints** | **Gateway** (S3, DynamoDB; free; route-table entry; endpoint policy) vs **Interface/PrivateLink** (most services: Kinesis, Glue, Athena, KMS, Secrets Manager, STS, Step Functions, Bedrock…; ENI + SG; hourly + per-GB cost) |
| NAT gateway | outbound internet from private subnets; fixed Elastic IP for partner allowlists; costs hourly + per-GB |
| Redshift | enhanced VPC routing forces COPY/UNLOAD traffic through VPC (endpoints/NAT) ~; publicly accessible = false; Firehose → Redshift requires publicly accessible cluster ✓ |
| Glue jobs in private subnet | S3 gateway endpoint (cheapest ✓), NAT/endpoints for other APIs |
Update security groups when: a job/ENI can't reach a database (open port from the job's SG), Lambda-in-VPC to RDS, MSK client access, Redshift from BI tool.

## 2. IAM groups, roles, endpoints, services (4.1.2, 4.1.4)
- **Principals**: users (avoid long-term keys), **groups** (permission bundles), **roles** (assumed; temporary credentials via STS). Prefer roles for services/workloads and **IAM Identity Center** for people ~.
- **Role anatomy**: *trust policy* (who can assume — e.g., `glue.amazonaws.com`, `lambda.amazonaws.com`, `states.amazonaws.com`, `redshift.amazonaws.com`, another account) + *permission policies* (what it can do). A Glue job role needs trust for Glue + S3/KMS/Catalog/Logs permissions; **`iam:PassRole`** is required for the identity that creates/starts the job.
- **Service roles for data services**: Lambda execution role (logs + source/target access), Glue job/crawler role, EMR service role + instance profile (EC2) + (EMR Serverless runtime role), Redshift role for COPY/UNLOAD/Spectrum (attach to cluster/namespace), Step Functions execution role (per-integration permissions), DMS (`dms-vpc-role`, endpoints roles) ~, Firehose delivery role, API Gateway execution/invocation role, CloudFormation service role (least-privilege deploys), CLI (profiles/SSO/assume-role) ✓ (4.1.4 names Lambda, API Gateway, CLI, CloudFormation).
- **Cross-account**: role in target account trusting the source account/role (then only the role's permissions apply) or resource policies (S3 bucket policy, KMS key policy, SQS/SNS policy, Lambda resource policy, Glue Data Catalog policy, Secrets Manager resource policy) + identity allow in source account.
- Guardrails: **permission boundaries** (max permissions of a role/user), **SCPs** (org-level deny/allow ceiling; never grant), session policies, conditions (`aws:SourceVpce`, `aws:PrincipalOrgID`, `aws:RequestedRegion`, `aws:SecureTransport`, tag keys).

## 3. IAM policies for endpoints and services (4.1.5)
- **VPC endpoint policy**: resource policy on an endpoint restricting what can be done through it (e.g., only the company's buckets) ✓ (topic-set Q49); combine with bucket policy `aws:SourceVpce` to force private path.
- **S3 Access Points**: per-application endpoints with their own policy (and VPC restriction), simplify shared-bucket permissions; **Multi-Region Access Points** ~; S3 Object Lambda ~.
- **PrivateLink**: interface endpoint to AWS services or your own endpoint service; security groups + endpoint policy; private DNS.
- Example (least-privilege S3 for a job):
```json
{"Version":"2012-10-17","Statement":[
 {"Effect":"Allow","Action":"s3:GetObject","Resource":"arn:aws:s3:::lake/raw/*"},
 {"Effect":"Allow","Action":"s3:PutObject","Resource":"arn:aws:s3:::lake/curated/*"},
 {"Effect":"Allow","Action":"s3:ListBucket","Resource":"arn:aws:s3:::lake","Condition":{"StringLike":{"s3:prefix":["raw/*","curated/*"]}}}]}
```

## 4. Credentials: create and rotate (4.1.3) ✓ [Secrets Manager rotation](https://docs.aws.amazon.com/secretsmanager/latest/userguide/rotating-secrets.html)
- **Secrets Manager**: store DB credentials/API keys; **automatic rotation** in two forms ✓: **managed rotation** (service-managed secrets, no Lambda) and **rotation by Lambda function** (other secret types; also managed external secrets for partners without Lambda ✓). Rotation updates the secret and the database/service; schedule in days; supports RDS, Aurora, Redshift, DocumentDB natively ~; cross-account via resource policy ~; KMS-encrypted; versions with staging labels (AWSCURRENT/AWSPENDING) ~.
- Use in data services: Glue connections, DMS endpoints, MSK SASL/SCRAM, Redshift (secret ARN for Data API/federated), Lambda env referencing the secret ARN (fetch at runtime; cache).
- No code changes needed if apps read the secret at runtime — answer to "rotate every 30 days without downtime" ✓ (mock Q17).
- Rotating **IAM access keys** (avoid: use roles); rotating **KMS** key material (4.3).

## 5. Managed vs unmanaged services (4.1.6)
Shared responsibility: with **managed** services (Glue, Athena, DynamoDB, Redshift Serverless, RDS, MSK Serverless) AWS secures/patches infrastructure and (for RDS) the OS and engine host; you manage data, identities, configuration, encryption settings, network exposure. With **unmanaged**/self-managed (Kafka on EC2, Spark on EC2, DB on EC2) you also patch OS, engines, HA, backups, scaling, encryption. Exam use: prefer managed for "least operational overhead", and know that "AWS patches RDS OS" ✓ vs "customer patches EC2 DB".

## 6. SageMaker Unified Studio domains, units, projects (4.1.7 — NEW) [secondary-verified]
- **Domain**: top-level boundary (organizational unit of governance): identity source (IAM Identity Center–based or IAM-based ~), blueprints/project profiles, default settings. Administrators manage users/groups and resources.
- **Domain units**: hierarchical grouping inside a domain (business units/teams) to delegate administration and policies ~.
- **Projects**: collaboration workspaces with members/roles, their own IAM role and resources (compute, storage, catalog assets); users "contribute to projects" ✓ (SMUS docs). Access to data flows through project membership and **catalog subscriptions** (4.5.6).
- Authentication: SSO (IAM Identity Center) or IAM credentials with the domain URL ✓.

## 7. Worked scenarios
1. *Glue job in private subnet, no internet, cheapest S3 access* → **S3 gateway endpoint**.
2. *Lambda in VPC with no NAT writes to Kinesis* → **interface VPC endpoint** for Kinesis.
3. *Only company buckets reachable through the S3 endpoint* → **VPC endpoint policy**.
4. *DB password rotates every 30 days, no job changes* → **Secrets Manager rotation** + Glue connection referencing the secret.
5. *Partner allowlists one IP* → **NAT gateway + EIP**.
6. *Hundreds of project prefixes, one policy* → ABAC (see 4.2).

## 8. Keyword → answer and traps
| Keyword | Answer | Trap |
|---|---|---|
| S3/DynamoDB private path, free | gateway endpoint | interface endpoint / NAT |
| Kinesis/Glue/KMS private path | interface endpoint | gateway |
| automatic credential rotation | Secrets Manager | Parameter Store |
| service assumes role | trust policy for service principal | permissions policy only |
| give a service a role | `iam:PassRole` | attach policy to service |
| org-wide ceiling | SCP | permission boundary on each role |
| managed = least ops | RDS/Glue/Athena | EC2-hosted |
