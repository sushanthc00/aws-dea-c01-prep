# Task 4.3 — Ensure data encryption and masking (D4)
Tags: ✓ verified 2026-10-20 (link) · ~ established, not re-fetched. Skills 4.3.1–4.3.4.

## 1. KMS essentials (4.3.2)
- **Key types**: AWS owned (invisible, service-managed), **AWS managed** (`aws/s3`, `aws/glue`…; created per service; policy not editable; **rotated every year automatically**, cannot be toggled ✓; cannot be used by other accounts ~ (standard rule)), **customer managed (CMK)** (you control policy, rotation, grants, aliases, deletion).
- **Key policy** is the root of trust for a KMS key; IAM policies work only if the key policy allows IAM (default statement enabling IAM) ✓. **Grants** = temporary, scoped delegation (used by AWS services such as EBS/RDS/Redshift). Use **aliases** to swap keys behind a name.
- **Envelope encryption**: `GenerateDataKey` → plaintext data key encrypts data locally, encrypted data key stored with the data; KMS `Encrypt` direct limit 4 KB ~. Services do this automatically.
- **Rotation** ✓ [KMS rotation](https://docs.aws.amazon.com/kms/latest/developerguide/rotate-keys.html): automatic rotation is optional for customer managed keys, only for **symmetric encryption keys with AWS_KMS-origin material**; default every **365 days**, custom **rotation period configurable** (and constrainable with `kms:RotationPeriodInDays`); **on-demand rotation** also available (also for imported-material symmetric keys); asymmetric, HMAC and custom-key-store keys need **manual rotation** (new key + alias swap). Key ID, ARN, aliases and policies **stay the same**; old key material is **retained** so old ciphertext still decrypts; rotation doesn't re-encrypt data or rotate data keys; billed for first and second rotation only; events in CloudTrail (`RotateKey`) and EventBridge ✓.
- **Multi-Region keys**: same key material in several Regions (DR, global tables, cross-Region replication) ~. **Imported key material** (BYOK), **custom key store** (CloudHSM) ~.
- Quotas: KMS API request rates are shared per account/Region — high-volume SSE-KMS workloads can throttle → use **S3 Bucket Keys** ✓ (fewer KMS calls) or data-key caching ~.

## 2. Encryption across account boundaries (4.3.3) ✓ [KMS external accounts](https://docs.aws.amazon.com/kms/latest/developerguide/key-policy-modifying-external-accounts.html)
Cross-account use needs **two permissions**: (1) the **key policy** (key account) allows the external account or specific principals; (2) an **IAM policy in the external account** delegates it. "The key policy determines who *can*; the IAM policy determines who *does*. Neither alone is sufficient" ✓. Cross-account permission applies only to crypto operations (Encrypt, Decrypt, ReEncrypt*, GenerateDataKey*), CreateGrant, DescribeKey, GetKeyRotationStatus, GetPublicKey, ListGrants, RetireGrant, RevokeGrant ✓ — other actions have no cross-account effect. Never `Principal: *` without conditions ✓. Cross-account calls are logged in both accounts' CloudTrail ✓. Use CMKs (AWS managed keys can't be shared).
```json
{"Sid":"AllowExternalAccount","Effect":"Allow","Principal":{"AWS":"arn:aws:iam::444455556666:root"},
 "Action":["kms:Encrypt","kms:Decrypt","kms:ReEncrypt*","kms:GenerateDataKey*","kms:DescribeKey"],"Resource":"*"}
```
Patterns: cross-account S3 SSE-KMS read (bucket policy/role + key policy + IAM kms:Decrypt) ✓ mock Q4; S3 CRR with SSE-KMS (replication role needs kms on source and destination keys; destination key set in config) ~; encrypted Redshift/RDS snapshot sharing/copy (share the CMK; cross-Region Redshift needs **snapshot copy grant** in destination Region) ~; Lake Formation shared tables on encrypted buckets need key access for consumers.

## 3. Encryption at rest by service
| Service | At rest |
|---|---|
| S3 | SSE-S3 default for new objects ~; **SSE-KMS** (audit, key control; Bucket Keys ✓); **DSSE-KMS** ~; **SSE-C** (client supplies key each request); client-side |
| Redshift | cluster encrypted with KMS (or HSM); enabling later via snapshot restore/migration; snapshots inherit |
| RDS/Aurora | at creation (KMS); snapshot copy to encrypt an unencrypted DB |
| DynamoDB | always encrypted: owned (default), AWS managed, or CMK |
| Kinesis Data Streams | SSE-KMS (rotation limits: 25 key changes/24 h ✓) |
| Firehose | CMK for up to 500 streams ✓; encrypts delivery to S3 via destination settings |
| Glue | **security configuration** (S3 output, CloudWatch Logs, job bookmarks) + Data Catalog encryption ✓ |
| EMR | security configuration (at-rest: S3 EMRFS, local disk/EBS; in-transit: TLS) |
| MSK | KMS at rest; TLS in transit |
| SQS/SNS | SSE-KMS |
| Athena | encrypt query results (workgroup-enforced SSE-S3/KMS/CSE-KMS) ~ |
| CloudTrail Lake | encrypted by default; optional own KMS key (cannot be removed or changed once set ✓) |
| Secrets Manager | KMS |

## 4. Encryption in transit or before transit (4.3.4)
- **In transit**: TLS/HTTPS to all AWS APIs; enforce on S3 with bucket policy `aws:SecureTransport = false` → Deny ✓; Redshift `require_ssl` and **TLS ≥ 1.2 enforced from 2026-10-31** ✓; RDS `rds.force_ssl` ~; MSK client TLS; Kinesis/Firehose HTTPS; VPC endpoints keep traffic off the internet; VPN/Direct Connect + MACsec ~; EMR in-transit via security configuration.
- **Before transit (client-side)**: encrypt data before sending — AWS Encryption SDK / S3 Encryption Client / KMS `GenerateDataKey` — when no service (or AWS) should see plaintext ✓ (mock Q64). DynamoDB Encryption Client ~.

## 5. Masking and anonymisation (4.3.1)
| Technique | Where |
|---|---|
| Static masking/redaction/hashing in ETL | **Glue sensitive data detection** transform (detect + mask/hash), DataBrew (mask, hash, substitute, shuffle), Spark UDFs, Lambda |
| Dynamic masking at query time | **Redshift dynamic data masking** (policy by role), LF data filters/column exclusion, Quick column-level security |
| Row/column restriction | Lake Formation filters, Redshift RLS, Quick RLS |
| Tokenisation/pseudonymisation | Lambda + KMS/HMAC, deterministic hashing for joinability |
| Anonymisation/k-anonymity/generalisation | aggregation, bucketing, noise (differential privacy ~), suppression |
| Discovery | **Macie** (S3), Glue sensitive data detection, catalog tags |
Compliance logic: mask **before** analytics zones for GDPR/HIPAA/PCI; keep re-identification keys separate; log access.

## 6. Worked scenarios
1. *High-volume SSE-KMS bucket throttles KMS and costs rise* → **S3 Bucket Keys** ✓.
2. *Account B role can't read account A SSE-KMS objects* → add key-policy statement (A) + IAM `kms:Decrypt` (B) ✓.
3. *CMK must rotate yearly with unchanged ID/alias* → enable **automatic rotation** ✓.
4. *Encrypted Redshift snapshots to another Region* → **snapshot copy grant** + destination KMS key.
5. *Support agents see last-4 card digits* → **Redshift dynamic data masking**.
6. *Regulation: AWS must never see plaintext* → **client-side encryption** before upload.

## 7. Keyword → answer and traps
| Keyword | Answer | Trap |
|---|---|---|

| AWS managed key cross-account | not possible → CMK | share aws/s3 |

| enforce HTTPS | `aws:SecureTransport` deny | default encryption |
