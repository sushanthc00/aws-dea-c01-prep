## 1. Optimise code to reduce runtime (1.4.1)
- **Lambda**: initialise SDK/DB clients **outside the handler** (reused across warm invocations); batch writes; reuse connections (RDS Proxy); more memory = more CPU (1 vCPU at 1,769 MB ✓); avoid heavy imports; use provisioned concurrency for cold starts; keep package small (zip 50 MB / 250 MB unzipped, image 10 GB ✓); ARM/Graviton for price-performance ~.
- **Spark/Glue**: filter early (pushdown predicates), select needed columns, broadcast small tables, avoid `collect()`/UDF row loops (prefer built-in functions/pandas UDF), tune shuffle partitions, repartition on join keys, handle skew (salting), cache only reused data, write fewer larger files (coalesce), use columnar formats.
- **SQL**: partition/sort-key filters, avoid `SELECT *`, pre-aggregate with MVs/CTAS, correct join order/keys, `LIMIT` for exploration, approximate functions (`approx_distinct`) ~.
- **I/O**: parallel multipart upload, byte-range reads, S3 prefixes for parallelism (3,500/5,500 req/s/prefix ✓), compression.

## 2. Lambda concurrency and performance (1.4.2) ✓ [Lambda quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html)
| Concept | Facts |
|---|---|
| Account concurrency | 1,000 default per Region (soft); new accounts start lower |
| Scaling | each function adds up to 1,000 execution environments per 10 s |
| **Reserved concurrency** | guarantees *and caps* a function's share (also protects downstream DBs) |
| **Provisioned concurrency** | pre-initialised environments → no cold start (schedule with Application Auto Scaling for predictable peaks) |
| Sync invoke rate | ≤ 10 × concurrency requests/s |
| Event source mappings | SQS: set **maximum concurrency** on the mapping; Kinesis/DynamoDB: **ParallelizationFactor 1–10** ✓, batch size, batching window ≤ 5 min ✓ |
| Memory/CPU | 128–10,240 MB; CPU ∝ memory; Lambda power tuning to find the cost/latency sweet spot ~ |
| Timeout | 900 s; payload 6 MB sync / 1 MB async |
| Throttling (429) | async: automatic retries (2) then DLQ/on-failure destination ~; sync: caller retries |
| Idempotency | at-least-once triggers (S3, Kinesis ESM ✓, SQS) → idempotent handlers (conditional writes, Powertools idempotency ~) |
Protecting a database from Lambda scale-out: cap concurrency (reserved or ESM max), RDS Proxy, SQS buffer.

## 6. AWS SAM (1.4.6)
`template.yaml` with `Transform: AWS::Serverless-2016-10-31`; resources `AWS::Serverless::Function`, `::StateMachine`, `::SimpleTable` (DynamoDB), `::Api`; commands `sam init`, `sam build`, `sam local invoke`, `sam deploy --guided`; event sources inline (S3, SQS, Kinesis, schedule). Use to package/deploy serverless data pipelines (Lambda + Step Functions + DynamoDB).
```yaml
Transform: AWS::Serverless-2016-10-31
Resources:
  Validate:
    Type: AWS::Serverless::Function
    Properties: { Handler: app.handler, Runtime: python3.13, MemorySize: 1024, Timeout: 120,
      Events: { Upload: { Type: S3, Properties: { Bucket: !Ref Landing, Events: s3:ObjectCreated:* } } } }
  Landing: { Type: AWS::S3::Bucket }
```

## 7. Mounting storage in Lambda (1.4.7)
- **Amazon EFS**: shared, persistent, POSIX file system mounted via access point; needs VPC config; use for large models/reference data updated outside deployments and shared by concurrent invocations.
- **/tmp ephemeral storage**: 512–10,240 MB per environment ✓, not shared, lost with environment.
- Layers (5 max, within 250 MB unzipped ✓) for libraries; container images up to 10 GB ✓; S3 for big objects (stream, don't load fully).

## 8. CI/CD for data pipelines (1.4.9)
CodePipeline (orchestrates stages) + CodeBuild (build/test/package, `buildspec.yml`) + CodeDeploy (Lambda/ECS/EC2 deployments, blue/green, canary/linear traffic shifting with alarms/rollback) + CloudFormation/CDK/SAM deploy; source: Git provider via connection (CodeCommit out ✓). Pipeline: lint → unit tests → package → deploy to dev → integration/data tests → approval → prod. Version artefacts (Glue scripts in S3 with version/prefix), use separate accounts per stage, parameterise env.

## 9. Distributed computing (1.4.10)
Split data into partitions processed in parallel (map), exchange data by key (shuffle), combine (reduce). Costs: shuffle (network + disk), skew (one hot key), small files, serialisation, memory spill. Techniques: partition by key, broadcast joins, salting, combiners/pre-aggregation, data locality (S3 is remote → minimise reads), idempotent tasks, fault tolerance by lineage/retry (Spark), checkpointing (Flink). Frameworks: Spark (Glue/EMR), Flink, Hive/Presto/Trino (Athena/EMR), MapReduce legacy.

## 10. Data structures and algorithms (1.4.11)
Know *where they appear*: **trees** (hierarchical data, B-tree indexes in RDS, partition/zone-map pruning), **graphs** (relationship traversal → Neptune; lineage graphs; DAG workflows in Airflow/Step Functions), **hash tables/partitioning** (shard routing by partition key hash, DynamoDB), **bloom filters** (dedupe, Parquet/ORC row-group skipping ~), **sorting/merge** (sort keys, compaction), **queues/streams** (SQS/Kinesis), **approximate nearest neighbour** (HNSW graph, IVF clusters — vector search, D2 2.1.8). Complexity intuition: O(n) full scan vs O(log n) index vs O(1) key lookup → pick DynamoDB/index for point lookups, columnar scans for aggregates.

## 11. Worked scenarios
1. *Lambda inserts rows; slow and costly* → move client init outside handler, batch inserts (and RDS Proxy).
2. *Same Glue job, IAM role, bucket across dev/test/prod* → parameterised **CloudFormation/CDK** template, pipeline per environment.
3. *Lambda needs to unzip an 8 GB archive* → ephemeral storage up to 10,240 MB ✓.
4. *SQS-triggered Lambda exhausts RDS connections* → ESM **maximum concurrency** + RDS Proxy.
5. *Java Lambda with 08:00 cold-start spike* → **provisioned concurrency** with scheduled scaling.

## 12. Keyword → answer and traps
| Keyword | Answer | Trap |
|---|---|---|
| reuse connections / faster Lambda | init outside handler, batching | more timeout |
| cap concurrency to protect DB | reserved concurrency / ESM max concurrency | memory increase |
| no cold start, predictable peak | provisioned concurrency | reserved |
| shared large mutable files | EFS | layer / zip |
| repeatable environments | CloudFormation / CDK | console clicks |
| serverless app package/test locally | SAM | plain CFN scripts |
| testing Spark logic fast | pure functions + pytest + small data | run full job |
| point lookup vs scan | key-value/index | full scan |
