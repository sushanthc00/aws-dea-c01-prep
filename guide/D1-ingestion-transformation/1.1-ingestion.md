## 1. Streaming ingestion — the service-selection core
**Concept (3 lines).** Streaming services differ on four axes: *replay*, *consumer model*, *latency*, *operations*. Pick by the axis the stem emphasises. Words like "replay", "multiple independent consumers", "ordering per key" point to a log (KDS/MSK); "load into S3/Redshift with no code" points to Firehose; "decouple/retry/DLQ" points to SQS; "fan-out" to SNS; "route events by content/schedule" to EventBridge.

| | Kinesis Data Streams | Amazon Data Firehose | MSK | SQS | SNS | EventBridge |
|---|---|---|---|---|---|---|
| Model | ordered log (shards) | delivery pipeline | Kafka log (partitions) | queue | pub/sub | event bus + rules |
| Replay | ✓ 24 h–365 d | ✗ | ✓ (retention set by you; Serverless unlimited ✓) | ✗ | ✗ | archive/replay feature ~ |
| Consumers | many; shared 2 MB/s/shard or EFO | none (destinations) | many consumer groups | competing | many subscribers | many targets |
| Ordering | per partition key | n/a | per partition | FIFO + MessageGroupId | FIFO topics ~ | no guarantee |
| Latency | ~100 ms; EFO ~70 ms ~ | ≥ 60 s buffer (60–900 s) ✓ | ms | ms | ms | ~sec |
| Ops | shards or on-demand | none | cluster or serverless | none | none | none |
When NOT: KDS for simple "land in S3" (use Firehose, cheaper in ops); Firehose when you need replay/ordering/custom consumers; MSK when you have no Kafka requirement (KDS is simpler); SQS when you need replay or multiple consumers of the same message.

## 2. Kinesis Data Streams (KDS)
Source: [KDS quotas](https://docs.aws.amazon.com/streams/latest/dev/service-sizes-and-limits.html) ✓
- **Provisioned shard**: write **1 MB/s or 1,000 records/s**; read **2 MB/s or 2,000 records/s** shared across classic consumers; **5 GetRecords calls/s/shard**; each call ≤ 10 MB / 10,000 records. **Record payload ≤ 10 MiB** (burst capacity for 1–10 MiB records). PutRecords ≤ 500 records / 10 MiB.
- **On-demand**: starts at 4 MB/s write / 8 MB/s read; scales to 10 GB/s w / 20 GB/s r in us-east-1, us-west-2, eu-west-1 (200/400 MB/s other Regions); 50 on-demand streams default; mode switch twice per 24 h. Provisioned: 20,000 shards/account in the three big Regions, 1,000 or 6,000 elsewhere.
- **Retention** 24 h (default) → 365 d. **EFO consumers**: 20 per stream (50 with On-demand Advantage). Shard iterator valid 5 min. Merge/split shards provisioned only.
- **Shard math** (memorise): shards = max( ⌈MB/s ÷ 1⌉, ⌈records/s ÷ 1,000⌉, ⌈consumer MB/s read ÷ 2⌉ ). Example: 6,000 rec/s × 500 B = 3 MB/s → bytes need 3 shards, records need **6** → 6 shards. Three classic consumers each reading all data of an 18 MB/s stream need 54 MB/s read > 2 MB/s × 18 shards = 36 → use **enhanced fan-out**.
- **Producers**: SDK (PutRecord/PutRecords), KPL (aggregation + batching, async), Kinesis Agent. **Consumers**: KCL (DynamoDB lease table, checkpointing, one worker per shard), Lambda, Managed Service for Apache Flink, Firehose.
- Hot shard: skewed partition key → higher-cardinality key or random suffix; `WriteProvisionedThroughputExceeded`. Lag: `GetRecords.IteratorAgeMilliseconds`.
- Security: SSE-KMS, TLS, interface VPC endpoint, IAM stream/consumer ARNs.

## 3. Calling Lambda from Kinesis (skill 1.1.7) ✓ [Lambda + Kinesis](https://docs.aws.amazon.com/lambda/latest/dg/with-kinesis.html)
- Lambda *polls* each shard (standard iterator ≈ once per second, shares the 2 MB/s) or receives pushed records over HTTP/2 from an **EFO** consumer. One batch per shard at a time; **in-order per shard; an error stops the shard** until the batch succeeds or expires (poison-pill).
- Batching: invokes as soon as records exist unless you set a **batching window up to 5 min**; stops at full batch or **6 MB** payload.
- **ParallelizationFactor 1–10** = concurrent batches per shard (ordering preserved per partition key) — the fix for rising IteratorAge with a fast function.
- Error handling knobs ~: BisectBatchOnFunctionError, MaximumRetryAttempts, MaximumRecordAgeInSeconds, on-failure destination (SQS/SNS/S3), tumbling windows for stateful aggregation.
- **At-least-once** → make the function **idempotent** (warned in docs ✓). Aggregated (KPL) records + EFO: records whose partition key doesn't match the aggregate key are **dropped** ✓ (edge-case, optional).
- Concurrency: reserve concurrency or request quota if the function can't keep up (shards × ParallelizationFactor concurrent batches).

## 4. Other streaming sources
**Amazon Data Firehose** (renamed from Kinesis Data Firehose) ✓ [Firehose quotas](https://docs.aws.amazon.com/firehose/latest/dev/limits.html)
- Buffer interval 60–900 s; record ≤ 1,000 KiB; PutRecordBatch ≤ 500 records or 4 MiB; Direct PUT default 500,000 rec/s / 2,000 req/s / 5 MiB/s in us-east-1, us-west-2, eu-west-1 (100,000 / 1,000 / 1 MiB elsewhere), auto-scales, no cap when the source is KDS. DirectPut retains 24 h if destination down.
- Features: Lambda transformation (5 concurrent invocations/shard), record format conversion JSON→Parquet/ORC using a Glue table ~, **dynamic partitioning** (500 active partitions/stream, 1 GB/s per partition), compression, backup of failed records to S3.
- Destinations: S3, Redshift (**publicly accessible clusters only** ✓), OpenSearch, Splunk, HTTP endpoint, Snowflake ~, Iceberg tables [UNVERIFIED]. Sources: Direct PUT, KDS, MSK ✓ (10 MB/s per partition; ≤ 6 MB records if Lambda enabled ✓), CloudWatch Logs/EventBridge etc. ~
- Pricing quirk ✓: ingestion billed per record rounded up to 5 KB → batch tiny records.
- Private Redshift + streaming? Use **Redshift streaming ingestion** (materialized view over KDS/MSK; concurrency scaling for KDS refresh ✓ P203 Aug 2026).

**Amazon MSK** ✓ [MSK quotas](https://docs.aws.amazon.com/msk/latest/developerguide/limits.html)
- Standard brokers: ≤ 30 brokers/cluster (ZooKeeper) or 60 (KRaft), 90/account, 1 GiB–16 TiB storage per broker, 3,000 IAM-auth connections/broker. **Express brokers**: unlimited storage, per-partition max 15 MB/s, instance-based throughput caps.
- **MSK Serverless**: 200 MB/s in, 400 MB/s out per cluster; **5 MB/s in / 10 MB/s out per partition**; 2,400 partitions (non-compacted); max message **8 MiB**; unlimited retention; 3,000 connections; IAM auth; 10 clusters/account.
- MSK Connect (managed Kafka Connect): ≤ 10 workers per connector. MSK Replicator for cross-cluster/Region copies. MSK Data Delivery channels to S3/S3 Tables (5–15 min freshness) ✓.
- Choose MSK when: Kafka APIs/ecosystem (Streams, Connect, MirrorMaker), existing apps. Auth: IAM, SASL/SCRAM (Secrets Manager), mTLS ~.

**DynamoDB Streams** ~: ordered item changes, 24 h retention, ≤ 2 simultaneous readers/shard ✓ (1 for global tables). Alternative: **Kinesis Data Streams destination for DynamoDB** (longer retention, many consumers, then Firehose to S3). EventBridge Pipes connects Streams to targets with filter/enrich ✓.

**DMS CDC** ✓ [DMS S3 target](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_Target.S3.html): modes full load, CDC, or both; targets include S3, Kinesis, Kafka/MSK, Redshift ~. S3 target writes **CSV by default, Parquet optional**; full-load files `LOAD00000001.csv…` and CDC files named by timestamp under `schema/table/`; control file size with `MaxFileSize`. Parallel full load / more subtasks speed large tables. CDC rows carry an operation column (I/U/D) ~.

**Glue streaming ETL** (Spark Structured Streaming micro-batches from KDS/Kafka, serverless; G.025X worker for small streams ✓) and **Redshift** (MV streaming ingestion) are also listed as streaming readers in skill 1.1.1.

## 5. Batch sources and configuration (1.1.2, 1.1.3)
| Source | How read | Notes |
|---|---|---|
| S3 | Glue/EMR/Athena/Redshift COPY/Lambda | prefix + partition pruning; avoid small files; S3 events for arrival |
| RDS/on-prem DB | Glue JDBC (partitioned read), DMS, zero-ETL (Aurora/RDS→Redshift ✓ ~) | read replica / snapshot export to protect OLTP |
| Redshift | UNLOAD to S3, Glue connector, data sharing | |
| SaaS | **AppFlow** (Salesforce, SAP, ServiceNow…; schedule/event/on-demand) | no code; zero-ETL for some SaaS ✓ (Glue docs) |
| Files from on-prem | **DataSync** (scheduled, verified, bandwidth-controlled), Transfer Family (SFTP/FTPS/FTP/AS2 endpoint), Snow Family (offline) | |
| EMR | Spark/Hive jobs reading HDFS/S3/EMRFS | |
**Batch configuration choices (1.1.3)**: incremental vs full (bookmarks, watermark columns, DMS CDC), file size/partitioning (128 MB–1 GB), parallel JDBC reads (partition column + bounds, `hashfield/hashpartitions`), retries/timeouts, schedule vs event, idempotent writes, compression, `fetchsize`, worker type/number, S3 `groupFiles/groupSize` for many small files.

## 6. Consuming data APIs (1.1.4)
Pull on a schedule from REST APIs: Glue Python shell/Lambda (≤15 min ✓) + EventBridge Scheduler; AppFlow for SaaS APIs. Handle **pagination**, **429/rate limits** (exponential backoff + jitter, SQS buffer with max concurrency), auth secrets in Secrets Manager, idempotent writes. Long (> 15 min) pulls → Glue Python shell or ECS/Fargate task via Step Functions.

## 7. Schedulers and event triggers (1.1.5, 1.1.6)
**EventBridge Scheduler** ✓ [Scheduler](https://docs.aws.amazon.com/scheduler/latest/UserGuide/what-is-scheduler.html): cron/rate/**one-time** schedules, **flexible time windows**, retry policy + max retention for failed triggers, **at-least-once** delivery, templated targets (SQS, SNS, Lambda, EventBridge) and **universal targets** (270+ services, 6,000+ API operations, e.g., start a Glue job/Step Functions directly). Time zone support ~ (scheduled *rules* are UTC-only ~).
Other: Glue triggers (scheduled/conditional/on-demand/EventBridge) and workflows; MWAA schedule_interval/sensors; time-based = cron on any of these.
**Event triggers**: S3 Event Notifications → Lambda, SQS, SNS, EventBridge ✓ (Glue job is *not* a direct destination → go via EventBridge/Lambda); EventBridge rules on AWS service events (Glue job state change, Step Functions). Pattern: S3 → EventBridge → Step Functions → crawler → job (event-driven, no polling).

## 8. IP allowlists (1.1.8)
Outbound fixed IP for sources that allow-list: **NAT gateway + Elastic IP** (private subnet jobs); give that EIP to the partner. Inbound control: security groups (stateful), NACLs (stateless), VPC endpoints/PrivateLink, S3 bucket policy `aws:SourceIp`/`aws:SourceVpce`. For Glue JDBC: connection with VPC/subnet/SG.

## 9. Throttling and rate limits (1.1.9)
| Target | Symptom | Pattern |
|---|---|---|
| DynamoDB | `ProvisionedThroughputExceededException` | on-demand or auto scaling; spread keys; batch writes; SDK retries with backoff |
| RDS | connection exhaustion / load | RDS Proxy, SQS buffer + limited Lambda max concurrency, read replica, bounded Glue parallelism |
| Kinesis | `Write/ReadProvisionedThroughputExceeded` | more shards/on-demand, better key, PutRecords/KPL, EFO |
| S3 | 503 Slow Down | > 3,500/5,500 req/s/prefix ✓ → prefixes, fewer files, backoff |
| Third-party API | 429 | SQS + max concurrency, Step Functions Map `MaxConcurrency`, Wait/Retry |
Universal answer shape: **buffer (SQS/Kinesis) + bound concurrency + exponential backoff with jitter + idempotency**.

## 10. Fan-in and fan-out (1.1.10)
Fan-in: many producers → one stream (partition keys, KPL, agents, IoT rules). Fan-out: KDS **EFO** ✓ (20/50 consumers), KDS → Firehose + Flink + Lambda in parallel, **SNS → SQS** per subscriber (independent retries, DLQ; filter policies), EventBridge rules with multiple targets, MSK consumer groups.

## 11. Replayability (1.1.11)
Design so any stage can be rerun: raw immutable zone in S3; stream retention (KDS ≤ 365 d ✓, MSK); idempotent loads (MERGE/upsert or stage-then-swap); deterministic transforms; reset Glue bookmarks; Iceberg snapshots/time travel; EventBridge archive; SQS cannot replay (use DLQ redrive). Firehose does not retain for replay (24 h buffer only when destination fails ✓).

## 12. Stateful vs stateless (1.1.12)
Stateless: per-record map/filter/parse (Lambda, Firehose transform). Stateful: needs memory across records — windows, dedupe, joins, sessionization — **Flink** (keyed state, checkpoints, exactly-once), Spark Structured Streaming, Lambda tumbling windows (small). State must be checkpointed; replays require idempotent sinks.

## 13. Worked scenarios
1. *18 MB/s stream, three independent consumers, bursty, least ops* → **KDS on-demand + enhanced fan-out** (shared reads would need 54 MB/s vs 36 MB/s available; provisioned adds planning).
2. *Private Redshift cluster, near-real-time from Kinesis, least code* → **Redshift streaming ingestion MV** (Firehose cannot target private clusters ✓).
3. *Partner drops a file at unknown time; run crawler then job once* → **S3 → EventBridge → Step Functions** (not hourly schedule, not polling).
4. *DB→S3 lake with ongoing changes, Parquet, no code* → **DMS full load + CDC to S3 (Parquet)**; for Aurora→Redshift use **zero-ETL**.

## 15. Keyword → answer and traps
| Keyword | Answer | Trap |
|---|---|---|
| replay, reprocess, many consumers | KDS / MSK | Firehose |
| near real time to S3, no code | Firehose | KDS + Lambda |
| existing Kafka | MSK | KDS |
| rising iterator age | ParallelizationFactor / EFO / shards | more memory |
| poison record blocks shard | bisect + retries + on-failure destination | more shards |
| Firehose → private Redshift | streaming ingestion MV | Firehose directly |
| fixed IP for partner allowlist | NAT + EIP | S3 gateway endpoint |
| DB CDC to lake | DMS (full load + CDC) | DataSync |
| SaaS ingest | AppFlow | custom Lambda |
