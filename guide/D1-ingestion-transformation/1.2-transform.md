## 1. Choosing the transformation engine (skill 1.2.5) — the most tested decision
| Engine | Best for | Not for | Ops | Cost model |
|---|---|---|---|---|
| **AWS Glue** (Spark) | serverless ETL, catalog-integrated, bookmarks, DQ, many connectors | very custom frameworks (HBase, Presto tuning), sub-second streaming | lowest for Spark | DPU-hours (per-second, min duration ~) |
| **Glue Python shell** | small scripts, API pulls, light pandas (1/16 or 1 DPU ~) | big data | none | cheap |
| **EMR** (EC2 / EKS / Serverless) | custom Spark/Hive/Presto/HBase/Flink, tuning, Spot, existing Hadoop code | "least ops" asks (EC2) | EC2 high; Serverless low | EC2/Spot hours; Serverless vCPU/GB-hours |
| **Lambda** | event-driven small transforms ≤ 15 min ✓, ≤ 10,240 MB ✓ | big joins/long jobs | none | per-ms |
| **Athena** (CTAS/INSERT/UNLOAD) | SQL ELT on S3, format conversion, compaction | custom code (use Spark notebooks) | none | per TB scanned |
| **Redshift** | SQL ELT where data already is; heavy joins; MVs | unstructured raw | low–medium | node/RPU |
| **Managed Service for Apache Flink** | stateful real-time | batch | low | KPU-hours |
| **DataBrew** | no-code cleaning/profiling | complex logic | none | per node-hour/session |
| **AWS Batch / ECS / EKS** | containerised custom jobs, long-running | simple SQL | medium | compute |
Decision shortcuts: "serverless Spark + JDBC + schedule" → Glue. "Custom libraries, occasional Spark, no cluster" → **EMR Serverless**. "Existing EKS, share capacity" → **EMR on EKS**. "HBase/specific frameworks" → EMR on EC2. "Convert CSV→Parquet with SQL only" → Athena CTAS (or Glue). "Real-time windows" → Flink.

## 2. AWS Glue essentials ✓ [Glue job properties](https://docs.aws.amazon.com/glue/latest/dg/add-job.html)
- **Versions** ✓: 6.0 (Spark 4.1.1, Python 3.13), **5.1 (Spark 3.5.6, Python 3.11; default for new jobs)**, 5.0, 4.0, 3.0. [Earlier cheatsheet note "5.1 current" → 6.0 now exists; exam-relevant fact is "newer versions give newer Spark/Python and open-table libraries".]
- **Job types**: Spark (`glueetl`), Spark Streaming (`gluestreaming`), Python shell (`pythonshell`).
- **Workers (DPU = 4 vCPU + 16 GB)** ✓: G.025X 0.25 DPU (streaming only, low volume) · **G.1X** 1 DPU (4 vCPU/16 GB) · **G.2X** 2 DPU (8/32) · G.4X 4 · G.8X 8 · G.12X 12 · G.16X 16; memory-optimised **R.1X–R.8X** for OOM-prone jobs (higher start latency). G.1X/G.2X cover most jobs.
- **Flex** ✓: flexible execution class for non-urgent jobs (Glue 3.0+, **G.1X/G.2X only**); billed per worker-time actually running; may start later. **Standard** for time-sensitive.
- **Timeout** ✓: configurable up to **7 days**; default 2,880 min (≤ Glue 4.0) or **480 min (5.0+)**; **retries 0–10**; timed-out jobs aren't retried. **Max concurrency** default 1 per job (error when exceeded) unless raised; **job run queuing** option waits for quota instead of failing.
- **Auto scaling** (Glue 3.0+ ~) adds/removes workers within max.
- **Bookmarks** ✓: remember processed data; need `transformation_ctx` + `job.commit()` ~. Not supported with LF **cell-level filters** ✓ (also push-down predicates, `enableUpdateCatalog`).
- Security configuration (KMS for S3 output, CloudWatch Logs, bookmarks) · Job metrics + observability metrics + continuous logging + Spark UI (set a Spark UI logs path) ✓ · "Use Glue Data Catalog as Hive metastore" option ✓ · Temporary path in S3 (used by Redshift reads/writes) ✓.
- **DynamicFrame** (schema-on-the-fly, `ResolveChoice`, `ApplyMapping`, `Relationalize` to flatten nested JSON) vs Spark DataFrame (fixed schema, richer API). Convert with `toDF()` / `fromDF()`.
- **Pushdown predicate** (`push_down_predicate` on partition columns) vs **server-side catalog partition predicate** (`catalogPartitionPredicate`) for tables with huge partition counts ~.
- **Glue Studio** (visual), notebooks/interactive sessions, **DataBrew** (visual recipes), **Data Quality** (DQDL), **Schema Registry**, **sensitive data detection** transform, **workflows/triggers**.

## 3. Amazon EMR (skills 1.2.5, 3.3.6)
- Deployment: **EC2** (full control; primary + core + task nodes), **EKS** (Spark as pods on shared Kubernetes), **Serverless** (no cluster; per-job). Cluster node roles: primary (coordinates), core (HDFS/storage — keep On-Demand), task (stateless compute — Spot).
- Storage: S3 via EMRFS (decoupled storage), HDFS for scratch. Use Glue Data Catalog as Hive metastore ✓ (EMR integration).
- Scaling: managed scaling / auto scaling; instance fleets with Spot diversification; log URI to S3 so logs outlive the cluster.
- Lake Formation fine-grained access on EMR (incl. June 2026 direct S3 data access with EMR 7.13+ ✓ [WN]).
- **Release support** ✓ [EMR extended support](https://aws.amazon.com/about-aws/whats-new/2026/09/emr-extended-support-migration/): extended best-effort security fixes through 2027-06-30 for 5.36 and 6.6–6.15, and through 2027-08-31 for 7.0–7.10 — know "older releases still supported, migrate".
- Use EMR when: custom frameworks (HBase, Presto/Trino tuning), very large clusters with Spot economics, existing Hadoop/Spark code, specific JARs. Avoid when stem says "least operational overhead" and Glue/Serverless fits.

## 4. Lambda for transformation
Limits ✓ [Lambda quotas](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html): 15 min, 128–10,240 MB (1 vCPU at 1,769 MB), /tmp 512–10,240 MB, payload 6 MB sync / 1 MB async, concurrency 1,000 default, 1,000 environments/10 s scaling, zip 50 MB/250 MB unzipped, image 10 GB, layers 5. Good for: S3-triggered validation, Firehose transforms, small enrichments, API glue. Bad for: multi-GB joins, > 15 min.

## 5. Athena and Redshift as transformation engines
- **Athena CTAS**: `CREATE TABLE ... WITH (format='PARQUET', partitioned_by=ARRAY['dt'], external_location='s3://...') AS SELECT ...`; `INSERT INTO`; `UNLOAD` to write query results; Iceberg `MERGE`/`OPTIMIZE`/`VACUUM` ~. Limits ✓: query string 262,144 bytes; reads ≤ 1 M partitions per scan.
- **Redshift ELT**: `INSERT ... SELECT`, `MERGE`, stored procedures, materialized views, Spectrum for S3, COPY/UNLOAD; best when joins/aggregations dominate.

## 6. Containers: EKS and ECS (skill 1.2.1)
Use containers for custom runtimes, long jobs (> 15 min), shared platforms. **ECS on Fargate**: serverless containers, easy with Step Functions `.sync`; **EKS**: Kubernetes ecosystem, **EMR on EKS** for Spark on shared clusters; **ECR** stores images; **AWS Batch** schedules container jobs on EC2/Fargate/Spot. Optimise: right-size CPU/memory, Spot (Batch/EKS node groups), autoscaling (HPA/Karpenter/Cluster Autoscaler ~), image size for startup, place near data (same Region/AZ to avoid transfer cost).

## 7. Connecting and integrating sources (1.2.2, 1.2.3)
- **JDBC/ODBC**: Glue connections (JDBC URL, secret in Secrets Manager, VPC subnet + SG); Redshift/Athena JDBC/ODBC drivers for BI; partitioned reads for parallelism; push filters to source; use read replicas.
- **Integrate multiple sources**: Glue ETL joining JDBC + S3 + SaaS (AppFlow lands SaaS in S3); Athena **federated query** (Lambda connectors; "managed connectors" 12 sources Apr 2026 ~); Redshift Spectrum + federated query; zero-ETL for supported pairs ✓ (Aurora/RDS/DynamoDB/SaaS → Redshift/lakehouse); DMS for continuous DB → lake.
- Catalog as integration layer: Glue Data Catalog tables consumed by Athena/EMR/Redshift Spectrum/Glue.

## 8. Cost optimisation while processing (1.2.4)
| Lever | How |
|---|---|
| Right engine | Lambda < 15 min, Athena for SQL, Glue for Spark, EMR Spot for scale |
| Don't pay for idle | serverless (Glue, EMR Serverless, Athena, Redshift Serverless), auto scaling, Glue auto scaling, terminate transient EMR clusters |
| Cheaper capacity | Glue **Flex** ✓, EMR **Spot task nodes**, Savings Plans/RIs for steady, Redshift reservations (Serverless 3-yr up to 45 % ✓) |
| Read less data | Parquet/ORC, compression, partition pruning, pushdown, column selection |
| Fewer, larger files | compaction, Firehose buffering, `groupFiles` |
| Reduce egress | same-Region processing, VPC endpoints (gateway free ✓) vs NAT charges |

## 9. Format conversion (1.2.6)
CSV/JSON → **Parquet (Snappy)** partitioned by date. Where: Glue write with `format="parquet"`; Athena CTAS; Firehose record format conversion (needs Glue table); EMR Spark. Why: columnar pruning, compression, predicate pushdown, lower scan cost. Avro for row-oriented streaming + schema evolution; ORC for Hive/Presto; JSON/CSV for interchange only. Gzip is not splittable; multiple files or columnar fix single-file bottlenecks. See `cheatsheets/06-formats-compression.md`.

## 10. Troubleshooting transformations (1.2.7)
| Symptom | Fix |
|---|---|
| Glue/Spark OOM on a few executors | data skew → salting, repartition, broadcast; or R.* / larger workers |
| Job reprocesses everything | bookmarks off/misconfigured; `transformation_ctx`, `job.commit()` |
| Slow listing / many tasks | small files → `groupFiles`/`groupSize`, compaction |
| One executor busy on single gzip file | non-splittable → split files/Parquet |
| S3 503 Slow Down | spread prefixes, fewer files, backoff ✓ |
| `AccessDenied` | role lacks S3/KMS/Glue permission; VPC endpoint policy |
| Cannot reach JDBC | subnet/SG/NAT/route; self-referencing SG ~ |
| Mixed types after upstream change | `ResolveChoice`, Schema Registry compatibility |
| Lambda timeout | > 15 min ✓ → Glue/Step Functions/Fargate; more memory = more CPU |
| Join slow | broadcast small side, AQE, correct join keys |
| Python import error in Glue | `--additional-python-modules` / `--extra-py-files` |
Monitoring: CloudWatch Logs (continuous logging), job metrics, Spark UI/history server, EventBridge Glue Job State Change → SNS.

## 11. Creating data APIs (1.2.8)
**API Gateway + Lambda + DynamoDB** for millisecond key lookups; API Gateway + Lambda + Athena (with cached/precomputed results) for analytics; throttling and usage plans protect backends; Cognito/IAM/Lambda authorizers for auth; Redshift Data API (HTTP, no drivers/connections ~) and Athena API for programmatic SQL; AppSync is out of scope ✓.

## 12. Volume, velocity, variety (1.2.9)
Volume → scale-out storage/compute, partitioning, columnar. Velocity → streaming (KDS/MSK/Flink), micro-batch. Variety → structured (tables), semi-structured (JSON/Avro/Parquet → DynamicFrame, SUPER), unstructured (documents/images/logs → S3 + schema-on-read, Macie/Textract/Comprehend for extraction). Pipeline design maps each V to a service choice.

## 13. LLMs in data processing (skill 1.2.10 — NEW in v1.1)
Exam stance: *integration patterns and trade-offs*, not API syntax (ML training/inference tasks are out of scope ✓ exam guide).
- Use cases in pipelines: classification/tagging of text, summarisation, entity/PII extraction, normalising messy fields, generating embeddings for vector stores, SQL generation assistance (Amazon Q).
- Where it plugs in: **Lambda or Step Functions task calling Amazon Bedrock** (InvokeModel/Converse) per record or batch; **Bedrock batch inference** (prompts in S3 → results in S3; cheaper and asynchronous for large nightly volumes ~); Glue/EMR jobs calling Bedrock in `mapPartitions` with throttling; **Bedrock Knowledge Bases** for managed RAG ingestion (S3 → chunk → embed → vector store); embeddings → Aurora pgvector / OpenSearch / MemoryDB / S3 Vectors ✓ (see D2 2.1.8/2.4.6).
- Operational concerns: throttling/quotas (retry with backoff, SQS buffering, max concurrency), token/cost control (batch, cache, smaller model), idempotency, data privacy (PII masking before prompts; VPC endpoints for Bedrock), output validation (schema checks, guardrails), non-determinism → store prompt/version with results.
- Pick: synchronous per-event enrichment → Lambda; bulk offline → batch inference; document Q&A → Knowledge Bases.

## 14. Worked scenarios
1. *2 TB/day CSV, custom PySpark, join to RDS, partitioned Parquet, no clusters* → **Glue Spark job** with JDBC connection, scheduled trigger (Lambda too small; EMR EC2 needs cluster; Athena can't do custom PySpark).
2. *Nightly job, can start hours late, reduce cost* → **Glue Flex** (G.1X/G.2X) ✓.
3. *Spark job on one 50 GB gzip file, one executor busy* → deliver multiple files or convert to Parquet (gzip not splittable).
4. *Classify 10 M tickets nightly, results to S3, not real time* → **Bedrock batch inference** (not per-record Lambda with unlimited concurrency).

## 16. Keyword → answer and traps
| Keyword | Answer | Trap |
|---|---|---|
| serverless Spark ETL | Glue | EMR on EC2 |
| non-urgent, lower price | Glue Flex | more workers |
| occasional Spark, own libs, no cluster | EMR Serverless | persistent EMR |
| Spark on existing Kubernetes | EMR on EKS | Glue |
| long container job, serverless | Fargate task via Step Functions `.sync` | Lambda |
| skewed key OOM | salting / repartition | add workers |
| many tiny files | groupFiles / compaction | bigger workers |
| mixed column types | ResolveChoice | drop column |
| bulk LLM scoring, offline | Bedrock batch inference | per-record sync calls |
