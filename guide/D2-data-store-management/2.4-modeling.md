## 1. Schema design (2.4.1)
### Redshift
| Decision | Guidance |
|---|---|
| **Distribution** | AUTO (default) · KEY on the common join column of two big tables (co-location; avoid skewed keys) · ALL for small, slowly-changing dimensions · EVEN when no join key |
| **Sort key** | compound (leading-column filters; typical `date`) vs interleaved (equal weight across columns; slower loads, rare) vs AUTO; zone maps skip blocks |
| Compression | encodings AUTO; Parquet/ORC for external |
| Keys | PK/FK **informational, not enforced** ~ |
| Semi-structured | SUPER type + PartiQL; array functions (nine new, Mar 2026 ✓ WN) |
| Modeling | star schema (fact + dimensions) for BI; denormalise to avoid joins; MVs for repeated aggregates |
Red flags: DISTSTYLE ALL on huge tables; KEY on a skewed column; unsorted regions → VACUUM/auto; many tiny INSERTs.

### DynamoDB ✓ [DDB quotas](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/ServiceQuotas.html)
- **Model from access patterns**. Partition key = high cardinality, evenly requested; sort key enables range queries/one-to-many; **single-table design** (entity type prefixes) reduces round trips.
- **GSI** (any attributes as keys, eventually consistent, own capacity, add anytime; ≤ 20 default ✓) vs **LSI** (same partition key, alternate sort key, strong reads, **created at table creation only**, 10 GB per item collection, ≤ 5 ✓). Sparse indexes (only items with the attribute). Project only needed attributes (≤ 100 projected non-key attributes ✓).
- Hot partitions: better keys; **write sharding** (random/calculated suffix); on-demand; adaptive capacity ~; burst. Inverted index via GSI (swap PK/SK).
- Access pattern example: orders by customer newest-first → PK `customerId`, SK `orderDate`; by order ID → GSI PK `orderId`; by status across customers → GSI PK `status`, SK `orderDate`. (An LSI cannot do this: shares `customerId`.)

### Lake Formation / lake tables
Databases/tables in the Glue Data Catalog on S3; partition on filter columns (date, region); columnar + compression; LF-tags on databases/tables/columns for governance; table formats (Iceberg) for evolution; layers raw → curated → consumption.

## 2. Changes to data characteristics (2.4.2)
Volume growth (partition/compaction, scale-out), velocity change (batch → stream), **variety/drift** (new columns, type changes, nested JSON), cardinality shifts (hot keys), data skew. Techniques: schema-on-read, Glue DynamicFrame `ResolveChoice`, Schema Registry compatibility modes, Iceberg schema/partition evolution (no rewrite), crawler policy Log, defensive parsing, backfills with idempotent jobs, monitoring DQ rules, alerts on schema drift.
- Athena/Parquet: **adding a trailing column** is compatible (old files → NULL); renaming/reordering depends on by-name vs by-position mapping ~.
- Avro: forward/backward/full compatibility (Schema Registry) ~.

## 3. Schema conversion (2.4.3) ✓ [DMS Schema Conversion](https://docs.aws.amazon.com/dms/latest/userguide/CHAP_SchemaConversion.html)
- **DMS Schema Conversion** = managed feature of AWS DMS that converts **schemas (not data)** from source engines to Aurora/RDS/Redshift targets; builds on the **AWS SCT** conversion engine (SCT itself was removed from the in-scope list ✓ but skill 2.4.3 still names it). Resources: **instance profile** (network/security), **data providers** (source/target), **migration project** (+ Secrets Manager secrets). Workflow: assess (assessment report shows what converts automatically vs manual) → convert → review/edit → apply to target or export SQL to S3. **Generative AI conversion** for hard objects on some paths (Oracle/SQL Server/Db2/SAP ASE → PostgreSQL). Extension packs emulate missing source features.
- Supported (examples ✓): Oracle → Aurora/RDS PostgreSQL, MySQL, **Redshift**; SQL Server → PostgreSQL/MySQL; PostgreSQL → MySQL; MySQL → PostgreSQL; Db2 LUW/z/OS → PostgreSQL; SAP ASE → PostgreSQL.
- Pair with **DMS data migration** (full load + CDC) — conversion first, then data.

## 5. Indexing, partitioning, compression, optimisation (2.4.5)
| Topic | Practice |
|---|---|
| Partitioning (lake) | by common filters, moderate cardinality; avoid minute/user_id partitions; Athena ≤1 M partitions/scan ✓; Hive-style `k=v` prefixes; partition projection |
| File layout | 128 MB–1 GB columnar files; compaction; avoid small files (S3 req limits ✓) |
| Compression | Snappy default for Parquet; ZSTD better ratio; gzip not splittable; BZIP2 slow |
| Redshift | sort/dist keys; MVs; ANALYZE/VACUUM (auto); compression encodings |
| DynamoDB | key design, GSIs, projections, TTL |
| RDS/Aurora | B-tree indexes, composite/covering indexes, partitioned tables, `EXPLAIN` ~; pgvector HNSW/IVF for vectors |
| OpenSearch | shards/replicas, ISM lifecycle ~ |
| Iceberg | hidden partitioning, sort order, compaction (`OPTIMIZE`), S3 Tables auto maintenance ✓ |

## 6. Vectorization (2.4.6 — NEW) and Bedrock Knowledge Bases
- **Vectorization** = turning text/images/audio into embeddings with an embedding model (e.g., Amazon Titan, Cohere Embed) so semantic similarity becomes vector distance. Pipeline: **ingest → chunk → embed → store (vector index) → retrieve top-K → augment prompt (RAG)**. Chunking strategy (size/overlap), metadata filters, re-embedding on model change (dimension must match index).
- **Amazon Bedrock Knowledge Bases** ✓ automates ingestion from S3: "converts unstructured text to chunks and vectors and stores it in a PostgreSQL database" when Aurora is the vector store ✓; other stores: OpenSearch (Serverless), S3 Vectors ~, etc.; queried by agents/RetrieveAndGenerate APIs ~.
- Dimension examples ✓: Titan v2 256/512/1024; Titan multimodal 1,536; Cohere Embed 1,024. DynamoDB vector index max 4,096 dims ✓.
- Choose: managed pipeline → Knowledge Bases; custom → Lambda/Glue calling Bedrock embeddings into pgvector/OpenSearch/MemoryDB; high recall → HNSW; cheap/low memory → IVF (see 2.1 §9).

## 7. Worked scenarios
1. *Redshift orders (2 B) ⋈ customers (500 M) on customer_id* → **DISTKEY(customer_id) both** (ALL on 500 M rows is wrong).
2. *Queries by customer newest-first and by order ID* → PK customerId / SK orderDate + **GSI on orderId** (LSI can't).
3. *Oracle → Aurora PostgreSQL, minimal downtime* → **DMS Schema Conversion** then **DMS full load + CDC**.
4. *New optional Parquet column; old partitions must keep working* → add column to table definition; old files return NULL.
5. *Upstream int → string* → **ResolveChoice** + schema registry/catalog versioning.
6. *RAG over S3 documents with minimal code* → **Bedrock Knowledge Bases**.

## 8. Keyword → answer and traps
| Keyword | Answer | Trap |
|---|---|---|
| co-locate join | KEY dist | ALL on big table |
| small dimension | ALL | KEY |
| range filter on date | sort key date | interleaved all columns |
| query by non-key attribute across partitions | GSI | LSI / Scan |
| hot DynamoDB key | write sharding | DAX (read cache) |
| heterogeneous DB migration | DMS Schema Conversion + DMS | DataSync |
| data lineage across projects | SageMaker Catalog | CloudTrail |
| too many partitions/small files | coarser partitions + compaction | more partition columns |
| vector recall vs memory | HNSW vs IVF | B-tree/GIN |
