## 1. Selection by access pattern (master table)
| Access pattern / need | Choose | Why | Not |
|---|---|---|---|
| Ad hoc SQL on rarely queried lake data | **S3 + Athena** | pay per TB scanned, no infra | provisioned Redshift |
| Repeated BI, complex joins, high concurrency, columnar warehouse | **Redshift** (+ Spectrum for cold S3) | MPP, MVs, concurrency scaling | RDS/Aurora |
| Key-value/document, known access paths, ms latency, any scale | **DynamoDB** | serverless, partition key design | relational joins |
| Relational OLTP, transactions, joins | **RDS / Aurora** | SQL, ACID, replicas | analytics at scale |
| Wide-column, Cassandra/CQL | **Keyspaces** | serverless Cassandra-compatible | DynamoDB (different API) |
| MongoDB-compatible documents | **DocumentDB** | | DynamoDB |
| Graph traversal (fraud rings, recommendations) | **Neptune** | multi-hop relationship queries | Redshift joins |
| Durable microsecond Redis-compatible primary DB | **MemoryDB** | multi-AZ durable, sorted sets, vector search ~ | S3 |
| Log/search/dashboards, near-real-time text | **OpenSearch Service** | inverted index, k-NN | Athena (latency) |
| Streams as storage (replayable log) | **KDS / MSK** | retention (KDS 24 h–365 d ✓) | S3 |
| Data lake files / archive | **S3** classes ✓ | 11 9's durability | EBS/EFS |
| Managed Iceberg tables | **S3 Tables** ✓ | auto maintenance | self-managed small files |
| Time series | (Timestream no longer in either scope list ✓) | treat as DynamoDB/S3+Athena/OpenSearch patterns | — |
Cost/performance levers: serverless vs provisioned, reservations, storage tier, compression, partitioning, caching (DAX, ElastiCache not in scope list).

## 2. S3 storage classes ✓ [S3 storage classes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/storage-class-intro.html)
| Class | Designed for | AZs | Availability | Min duration | Min size | Retrieval |
|---|---|---|---|---|---|---|
| Standard | frequent, ms | ≥3 | 99.99 % | none | none | none |
| Intelligent-Tiering | unknown/changing patterns | ≥3 | 99.9 % | none | monitoring fee; **objects < 128 KB not monitored** | **no retrieval fee**; tiers: Frequent → Infrequent (30 d) → Archive Instant Access (90 d) → optional Archive Access (≥ 90 d) / Deep Archive Access (≥ 180 d, need RestoreObject) |
| Standard-IA | infrequent monthly, ms | ≥3 | 99.9 % | **30 d** | **128 KB** | per-GB fee |
| One Zone-IA | re-creatable infrequent, ms | **1** | 99.5 % | 30 d | 128 KB | per-GB fee; not AZ-resilient (good CRR replica target) |
| **Express One Zone** | single-digit-ms hot data, directory buckets | **1** | 99.95 % | none | none | up to 10× faster, 50 % lower request cost than Standard |
| Glacier Instant Retrieval | quarterly, ms | ≥3 | 99.9 % | **90 d** | 128 KB | per-GB fee |
| Glacier Flexible Retrieval | yearly, min–hours | ≥3 | 99.99 % after restore | **90 d** | 40 KB metadata/object (8 KB Standard + 32 KB Glacier) | restore needed (Expedited / Standard / Bulk ~) |
| Glacier Deep Archive | < yearly, hours | ≥3 | 99.99 % after restore | **180 d** | 40 KB metadata | restore needed (Standard / Bulk ~) |
All Standard-family classes: 11 nines durability. Early deletion/transition → pro-rated charge ✓. S3 request rates ✓: 3,500 writes / 5,500 reads per second per prefix. Reduced Redundancy: don't use ✓.
Shortcuts: "unknown pattern, no retrieval fees" → **Intelligent-Tiering**; "quarterly, ms" → **Glacier IR**; "re-creatable, cheaper than IA" → **One Zone-IA**; "archive, hours OK, cheapest" → **Deep Archive**; "ML training hot data single-AZ ms" → **Express One Zone**.

## 3. Amazon Redshift (2.1.1, 2.1.2, 2.1.5)
- **Provisioned (RA3, managed storage)** for steady load/reservations; **Serverless** (RPUs) for spiky/dev, 3-year reservations up to 45 % ✓ (Feb 2026). **Concurrency scaling** for read bursts. Security/TLS ≥1.2 enforced since 2026-01-31 ✓.
- **Spectrum**: query S3 via external schemas/tables in the Glue Data Catalog; join with local tables; cold-data tiering (UNLOAD old data → Parquet → Spectrum).
- **Federated query**: live read of RDS/Aurora PostgreSQL & MySQL. **Materialized views**: precompute; auto refresh; can sit on Spectrum/external tables ~; streaming ingestion MVs from KDS/MSK ✓.
- **Data sharing** ✓ [Redshift data sharing](https://docs.aws.amazon.com/redshift/latest/dg/datashare-overview.html): live, transactionally consistent access **across clusters, serverless workgroups, AZs, accounts and Regions with no copy**; share databases/schemas/tables/views (regular, late-binding, materialized)/SQL UDFs/stored procedures; **read AND now write** (INSERT/UPDATE) shares (older material says read-only); use cases: central ETL → many BI clusters (workload isolation + chargeback), dev/test/prod sharing, Data Exchange licensing. Steps: producer `CREATE DATASHARE`, add objects, `GRANT USAGE ON DATASHARE … TO ACCOUNT/NAMESPACE`, (cross-account: authorize), consumer `CREATE DATABASE … FROM DATASHARE`.
- **Zero-ETL** from Aurora/RDS/DynamoDB/SaaS into Redshift ✓ (continuous, no pipeline).
- Python UDFs: end of support after 2026-06-30 ✓ → Lambda UDFs.
Deep Redshift design (dist/sort keys, COPY/UNLOAD, WLM, troubleshooting): `cheatsheets/07-redshift.md`, §D2 2.4.

## 4. Amazon DynamoDB (2.1.2) ✓ [DDB quotas](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/ServiceQuotas.html)
- Capacity: **on-demand** (unpredictable, least ops) vs **provisioned + auto scaling** (+ reserved capacity) for steady predictable load = cheapest. Defaults ✓: 40,000 RCU/WCU per table; 80,000 per account (provisioned); 2,500 tables/Region; 5 LSI; 20 GSI; ≤ 2 Streams readers per shard; PITR to any second within up to 35 days ~; global tables (MREC/MRSC) for multi-Region; TTL free expiry; DAX read cache ~.
- RCU/WCU maths ~: 1 RCU = one strongly consistent 4 KB read/s (eventual = ½, transactional = 2×); 1 WCU = one 1 KB write/s (transactional 2×). Item max 400 KB ~.
- Design rule: start from query list. See 2.4 for key design, GSIs, hot partitions.
- Vector indexes ✓ (DynamoDB quotas page): ≤ 5 per table, ≤ 4,096 dimensions, TopK ≤ 100, ≤ 18 inline filters.

## 5. RDS / Aurora (2.1.1, 2.1.3)
RDS engines (MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, Db2 ~) — Multi-AZ (failover standby; sync), read replicas (async, scale reads). **Aurora**: shared distributed storage, up to 15 replicas ~, fast failover, Global Database, serverless v2, **Aurora PostgreSQL + pgvector** ✓. RDS Proxy pools connections (Lambda/serverless clients). Zero-ETL Aurora/RDS → Redshift. Choose Aurora when you need higher scale/HA/replicas or pgvector HNSW; RDS when engine-specific compatibility (Oracle/SQL Server) or simple lift-and-shift.

## 6. Open table formats and S3 Tables (2.1.7 — NEW v1.1)
| | Iceberg | Delta Lake | Hudi |
|---|---|---|---|
| Strengths | hidden partitioning, partition & schema evolution, snapshots (time travel/rollback), ACID, engine-neutral | ACID + time travel, Spark-centric | record-level upserts, incremental pulls, COW/MOR |
| Support | Athena, Redshift, EMR, Glue, Snowflake… | Glue/EMR/Athena | Glue/EMR/Athena |
Glue 5.1 bundles Iceberg 1.10.0, Hudi 1.0.2, Delta 3.3.2 ✓.
**S3 Tables** ✓ [S3 Tables](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-tables.html): new **table bucket** type; tables stored as **Apache Iceberg** (incl. V3: deletion vectors, row lineage, column defaults, variant/geometry/geography/nanosecond timestamps); higher TPS and query throughput than self-managed tables in general-purpose buckets; **automatic maintenance** (compaction, snapshot management, unreferenced-file removal; configurable); IAM/SCP in the **`s3tables`** namespace, table-level policies; **Block Public Access always on**; integrates with Glue Data Catalog → Athena, Redshift, EMR, Glue, Quick, Lake Formation, SageMaker Unified Studio; Intelligent-Tiering for tables; replication of tables.
Iceberg operations in Athena ~: `CREATE TABLE … TBLPROPERTIES('table_type'='ICEBERG')`, `MERGE`, `DELETE`, `OPTIMIZE … REWRITE DATA USING BIN_PACK`, `VACUUM`, time travel `FOR TIMESTAMP AS OF`. Governed tables (old LF feature) → replaced by Iceberg.
Pick: need ACID/upserts/time travel on S3 → Iceberg; least ops managed Iceberg → **S3 Tables**; heavy upsert/CDC on Spark → Hudi (or Iceberg MERGE); Databricks interoperability → Delta.

## 8. Locks (2.1.6)
- **Redshift**: DDL/TRUNCATE take exclusive locks; long open transactions block others; find with `STV_LOCKS`, `SVV_TRANSACTIONS`, `STV_RECENTS`; clear with `PG_TERMINATE_BACKEND(pid)`; keep transactions short; concurrent writes serialize per table (snapshot isolation / serializable ~).
- **RDS/Aurora**: row/table locks, deadlocks (InnoDB, PostgreSQL); resolve by consistent access order, short transactions, retries; inspect `SHOW ENGINE INNODB STATUS` / `pg_locks`/`pg_stat_activity` ~.
- **DynamoDB**: no locks; use **conditional writes** (optimistic locking with a version attribute) and transactions.

## 9. Vector index types (2.1.8 — NEW) and where vectors live (2.1.3)
- **Embedding**: model-generated numeric vector; similarity metrics: cosine, L2 (Euclidean), inner product. Exact kNN is O(n); **approximate** nearest neighbour (ANN) trades recall for speed.
- **HNSW** (Hierarchical Navigable Small World): multi-layer proximity graph; **high recall, fast queries, more memory, slower build**; tunables m, ef_construction (recommended 256 with pgvector ≥ 0.6.0 ✓), ef_search. **IVF/IVFFlat**: k-means style clusters (lists); query probes nearest lists (probes); **faster build, less memory, lower recall at same latency, needs data first** ~.
- Aurora PostgreSQL ✓ [Aurora pgvector / Bedrock KB](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/AuroraPostgreSQL.VectorDB.html): `CREATE EXTENSION vector;` (**pgvector ≥ 0.5.0 for HNSW**); `CREATE INDEX … USING hnsw (embedding vector_cosine_ops) WITH (ef_construction=256);` supported in Aurora PostgreSQL 16.1+, 15.4+, 14.9+, 13.12+, 12.16+; table typically `(id uuid pk, embedding vector(n), chunks text, metadata json, custom_metadata jsonb)` with GIN index on `to_tsvector('simple', chunks)`; embedding dimensions: Titan v2 256/512/1024, Titan multimodal 1536, Cohere Embed 1024 ✓; requires RDS Data API + Secrets Manager secret when used as a Bedrock Knowledge Base.
- Other vector stores: OpenSearch (k-NN), **MemoryDB** (vector search, durable, µs) ~, **DynamoDB vector indexes** ✓, **S3 Vectors** (GA Dec 2025; low-cost large scale ~), Bedrock Knowledge Bases (managed). **MemoryDB** also the answer for "fast key/value with durability".
- Pick: SQL app + relational joins → Aurora pgvector (HNSW for recall); managed RAG → Knowledge Bases; ultra-low latency/leaderboards → MemoryDB; cheap huge cold vector sets → S3 Vectors.

## 10. Worked scenarios
1. *50 TB history, a few ad hoc queries/month, least cost, no infra* → **S3 Parquet + Athena**.
2. *Quarterly access, ms retrieval, 5-year retention* → lifecycle Standard → **Glacier Instant Retrieval** (90-day minimum satisfied) ✓.
3. *Unknown/changing access, no retrieval fees, >128 KB objects* → **Intelligent-Tiering**.
4. *Producer team shares Redshift tables live with another account* → **data sharing** (not UNLOAD/snapshot).
5. *Aurora PostgreSQL semantic search, 5 M embeddings, best recall* → **pgvector HNSW**.
6. *Cassandra app, serverless, minimal change* → **Keyspaces**; *fraud rings* → **Neptune**; *Redis-compatible durable* → **MemoryDB**.
